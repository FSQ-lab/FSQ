# Module: environments

## Purpose

Own host/runtime discovery, support classification, read-only readiness checks, and target discovery. Platform automation, package installation, and Workspace persistence are outside this module.

## Dependencies

- `models`: runtime status facts and pure Web channel identity contracts.
- Python standard-library host, filesystem, import, and subprocess facilities.
- Optional `appium-connect-agent` (`appium_connect_agent.contracts.LocalSettings`, `appium_connect_agent.runtime.Runtime`, and `appium_connect_agent.automation.list_ios_devices`), imported lazily for static `Runtime.diagnose(target_driver="mac2" | "xcuitest")` package and peer-compatibility inspection without mutating Workspace configuration or `~/.appium-connect-agent/` component and record directories (acquiring only the upstream account coordination lock `runtime.lock`) and bounded read-only iOS Simulator / physical device discovery on macOS hosts.

The module must not import Application, adapters, Config persistence, concrete drivers or harnesses, LLM providers, or Execution.

## Public Interface

`PlatformRuntimeService` is the stable service for read-only Runtime `check`, exact-channel Web executable discovery, explicit executable validation, platform Target configuration/availability diagnosis from resolved settings, and ordered platform prerequisite diagnosis. Target and prerequisite diagnosis return safe normalized status facts without env values, unrestricted local target details, raw subprocess output, or backend objects. `PlatformRuntimeCheck` and `PlatformPrerequisiteCheck` remain owned by Models. Core's legacy export references the canonical service class.

`AndroidDeviceDiscovery` is the canonical stable discovery service, exported here and re-exported by Core for compatibility. It returns model-owned `AndroidDeviceDiscoveryResult` facts and never selects or persists a device. Device serial and allowlisted model/transport metadata are returned only as necessary transient selection identities, not interpolated into unrelated errors or remediation commands.

`IOSDeviceDiscovery` is the canonical stable iOS discovery service, exported here and re-exported by Core for compatibility. It delegates to public `appium_connect_agent.automation.list_ios_devices`, returns model-owned `IOSDeviceDiscoveryResult` facts (`udid`, `name`, `kind`, `platform_version`, `state`, `interface`), and never selects, boots, or persists a device.

The public runtime boundary exposes bounded read-only application inventory collection and concrete target validation for Quick Test.

- `list_applications(*, platform, target_id=None, windows_catalogue=None, force_refresh=False) -> ApplicationInventoryResult`: collects a bounded, deduplicated, deterministically ordered inventory for `android`, `ios`, `macos`, or `windows`, cached in-process per `(platform, target_id)` with host-owned TTL/invalidation (never caching semantic intent). Each candidate has a deterministic host-assigned `candidate_id`, display `label`, optional localized/source `aliases`, concrete native identity (`app_id`, `bundle_id`, `app_path`), `source`, and optional host-only Windows `window_title_re`. `force_refresh=True` bypasses the cache.
  - Android collects installed packages on the selected online authorized device through the existing-server-only ADB transport, prioritizing third-party packages to reduce noise while retaining package identity and available display/label metadata.
  - iOS scopes the query and `(ios, target_id)` cache to the exact selected usable device. Simulator inventory contains system and third-party apps by bundle ID, with display/localized name metadata when available. Physical-device inventory uses only an already-supported read-only lookup, if available; unsupported enumeration is an explicit outcome, not a successful empty inventory or a failed query. It does not populate the successful inventory cache.
  - macOS scans `/Applications`, `/System/Applications`, and `~/Applications` (bounded depth and count) and reads `Info.plist` plus localized `InfoPlist.strings` display names (`CFBundleDisplayName` / `CFBundleName`).
  - Windows merges bundled `applications.windows.yaml` presets (retaining each preset's `window_title_re` as host-only metadata when a declared path candidate exists), registry `App Paths` (`HKCU`/`HKLM`, 32/64-bit views), and Start Menu `.lnk` shortcut target resolution into deduplicated executable candidates.
- `lookup_application(*, platform, name, explicit_reference=None, target_id=None) -> ApplicationLookupResult`: validates an explicit concrete native identity or path (Android package on selected device, macOS bundle ID or `.app`/executable path, Windows absolute `.exe` path) under the same read-only, bounded host/device rules.
  - iOS validates an exact bundle ID or an absolute local `.app` directory for a booted Simulator, checking bounded `Info.plist` data and its bundle identity. `.ipa` and physical-device package paths are not Quick Test references. A Simulator bundle ID must be confirmed installed. A physical-device bundle ID without a supported read-only installation check is validated for legal identity on the selected connected device but remains explicitly unverified for installation; when supported, the check's absence and error facts are preserved.

Validation establishes concrete existence and runtime prerequisites, not the correctness of a model's semantic interpretation. Discovery does not promise every alias or arbitrary installation location, never performs a full-disk scan, and remains internal to Application coordination rather than a browser-visible installed-app catalog.

## Internal Structure

- `__init__.py`: public exports only.
- `_service.py`: platform-neutral dispatch and normalized result coordination.
- `PlatformRuntimeService.check_prerequisites` accepts explicit `application_pending: bool = False`, `require_explicit_selection: bool = False`, and `sandbox: Literal["wsb"] | None = None` keyword context; native providers remain the prerequisite-fact authority.
- `_android_devices.py`, `_ios_devices.py`: canonical Android and iOS discovery services delegating to private read-only providers.
- `_applications.py`: implementation of `PlatformRuntimeService.list_applications` (including process-local `(platform, target_id)` environment inventory cache and `force_refresh`) and `PlatformRuntimeService.lookup_application`, returning Models-owned `ApplicationCandidate`, `ApplicationInventoryResult`, and `ApplicationLookupResult` facts.
- `providers/`: private Android, Web, Windows, macOS, and iOS runtime mechanics.

## Python Architecture

- Architecture level: Level 3 Layered Application.
- Public API: `PlatformRuntimeService`, `AndroidDeviceDiscovery`, and `IOSDeviceDiscovery`.
- Internal modules: service implementation and platform providers.
- Domain boundaries: host support/readiness and target discovery only.
- Boundary models: normalized status facts come from `models`.
- Dependency direction: Application depends on Environments; Environments depends on Models, never Application or adapters.
- Rationale: the service coordinates host-specific discovery and normalized readiness failures.

## Error Handling

Readiness checks never install or modify software. Missing Python platform dependencies identify an incomplete `fsq-agent` installation and provide safe reinstall/repair guidance. Missing external host services or system prerequisites provide safe provisioning guidance without executing it.

Target configuration diagnosis validates required identities and local path/channel shape. Target availability uses read-only discovery for current candidates, including Android online/authorized device and application discovery, without installing applications, changing device state, starting a browser/application, or creating a Driver/Appium session.

Application inventory collection and explicit lookup bound query input, candidate count, metadata bytes, and elapsed time. A truncated, malformed, unsupported, timed-out, or partially failed discovery cannot establish a valid inventory or candidate and is never reported as a successful empty match. Zero and multiple matches remain distinct discovery facts for Application to handle. Missing display-name metadata alone does not invalidate an otherwise valid concrete native identity. Discovery does not silently choose a fallback candidate, substitute a missing reference, invoke a shell from prompt text, expose inventories to browser clients, mutate application state, install applications, or weaken existing Android no-daemon-start and desktop host restrictions.

macOS prerequisite diagnosis performs bounded read-only host inspection and returns details in this order: `xcode_installation`, `xcode_developer_directory`, `appium_connect_runtime`, `application_path`, and `bundle_identifier`. It distinguishes a full Xcode application from Command Line Tools, verifies that the active developer directory belongs to full Xcode, performs zero-subprocess, zero-network static inspection of `appium-connect-agent` package importability, unambiguous `node` executable resolution on `PATH` (without reading `~/.appium`), and the fixed account managed root `~/.appium-connect-agent/` (`records/installation.json` complete with verified Appium 3.7.0, idle/settled `records/service.json` and `records/maintenance.json`, and installed `driver-home/node_modules/appium-mac2-driver` compatible with Appium 3.7.0 via `Runtime.diagnose(target_driver="mac2")`, without mutating Workspace configuration or `~/.appium-connect-agent/` component and record directories beyond acquiring the upstream account coordination lock `runtime.lock`), validates the configured application bundle or executable path, and checks that a configured concrete bundle identifier resolves consistently with the configured application when both are present (marking `bundle_identifier` ready with dynamic frontmost-attachment disclosure when `bundle_id` is `"auto"` and `app_path` is unset). A prerequisite blocked by an earlier prerequisite is `not_applicable` with safe guidance rather than a fabricated ready result.

A valid active full-Xcode developer directory proves installation even outside standard application folders. Each host probe isolates unexpected errors into its own safe `error` fact and preserves other independent results. Invalid or non-dictionary application plists fail bundle identity verification without falling back to another installed application. For an executable within an application bundle, that enclosing bundle supplies its identity; path-only targets do not require a separate bundle identifier.

macOS prerequisite facts include explicit copyable repair commands only where a safe, applicable command can be supplied (such as Python API managed runtime installation `Runtime(LocalSettings(...)).install(InstallRequest())`, explicit Mac2 driver installation `Runtime(LocalSettings(...)).ensure_managed_driver("mac2")`, or managed cleanup `Runtime(LocalSettings(...)).cleanup_installation()`). Custom Xcode installations receive guidance that respects their configured values; a default-path command must not be presented as the exact fix for a different configuration. Commands never contain credentials or private target values and are never executed by diagnosis. Web prerequisite checks and default (non-sandbox) Windows prerequisite checks are empty.

### Android diagnosis

- Ordered details are `adb_cli`, `appium_connect_runtime`, `adb_server`, `device_connection`, `device_selection`, `application_identifier`, and `application_installation`. Independent local checks run even when downstream checks are blocked. Blocked checks use `not_applicable` with their dependency reason and are not counted as passed. Stable optional prerequisite codes distinguish concrete failures beyond the four existing display statuses.
- ADB executable availability is checked without changing PATH. `appium_connect_runtime` performs strictly read-only, zero-subprocess, zero-network, zero-mutation inspection of `appium-connect-agent` package importability, the fixed account managed root `~/.appium-connect-agent/` (`records/installation.json` complete with verified Appium 3.7.0 and `appium-uiautomator2-driver` 8.7.0, plus idle/healthy `records/service.json` and `records/maintenance.json` state), unambiguous `node` executable resolution (`Runtime(LocalSettings(node_executable=...)).diagnose()` resolves the first executable `node` in `PATH` order explicitly so multi-entry `PATH` environments are not misclassified as `ambiguous_candidates`, while never reading `~/.appium`), and host Android SDK / JDK layout readiness needed for managed UiAutomator2 sessions (propagating resolved `android_sdk_root` and `java_home` from trusted host environment or probing available JDK layout when `JAVA_HOME` is unset). Package absence identifies an incomplete FSQ installation; uninitialized or recovery-required managed root state provides accurate Python API repair guidance (`Runtime(LocalSettings(...)).install(InstallRequest())`) and never directs users to nonexistent CLI subcommands such as `appium-connect-agent install`.
- Server diagnosis and device inventory use a shared bounded ADB protocol client that only connects to an already-running server. No `adb devices`, `adb shell`, `adb start-server`, backend auto-connect, or retry helper capable of spawning/restarting a daemon runs during diagnosis, target discovery, or startup preflight. Checking a socket and subsequently invoking an auto-starting client is not sufficient: if the server disappears between requests, diagnosis fails safely without restarting it.
- The default endpoint is local IPv4 loopback port 5037. Trusted process-level `ANDROID_ADB_SERVER_HOST` and `ANDROID_ADB_SERVER_PORT` values use the same endpoint as the Android backend. Absent values use the defaults; explicitly blank or malformed values are rejected. IPv6 endpoints are unsupported while the selected Android backend uses IPv4 sockets. Invalid, conflicting, unsupported socket forms (including `ADB_SERVER_SOCKET`) or non-loopback endpoint overrides are reported unavailable with guidance; they are never silently ignored in favor of another server. Browser and Workspace payloads cannot supply ADB hosts, ports, socket paths or commands. No new persisted endpoint configuration is introduced.
- All transport reads, protocol framing, subprocess-free package queries, response sizes and total probe durations are bounded. Malformed/truncated responses and timeouts are errors, not empty successful inventories. Refused or disappeared servers are unavailable; wrong protocol or incompatible responses remain distinct safe errors. Sockets close on success, failure and cancellation/timeout.
- Inventory preserves offline, unauthorized and other non-online states with actionable guidance. A selected serial must match exactly one currently online authorized device; absence, unauthorized and offline states are distinguished. No explicit selection resolves only when there is exactly one online authorized device. Multiple online devices require selection; the presence of another offline device does not invalidate a sole usable choice. A selected device never falls back to a different online device.
- Application identity is independently validated as a bounded package identifier. A fixed, safely encoded read-only package-manager query runs through the existing-server transport only for the selected authorized device. Explicit package paths prove installation; only a successful, well-formed negative response proves absence. Timeout, permission denial, nonzero exit and malformed output are query errors and block readiness without claiming the app is uninstalled. App IDs and serials cannot inject commands.
- Prerequisite facts are reused within one diagnosis so discovery and package results are not independently re-queried for summary construction. Any required unavailable/error fact or blocked required dependency prevents the Android target from becoming ready. Provider policy remains Application-owned.
- Safe guidance covers platform-tools setup, incomplete FSQ installation, managed `appium-connect-agent` runtime preparation (`Runtime.install(InstallRequest())`), Node.js/JDK prerequisites, manual ADB server startup, USB debugging/authorization, reconnection, explicit device selection and app installation/configuration repair. Commands are copy-only, host-appropriate and contain no private device/app values; parameterized instructions requiring user substitution remain explanatory text. No automated permission changes, reconnect/restart, app install, device reboot, forwarding, managed Appium startup, `Runtime.install(...)` execution, or Appium session creation occurs during diagnosis.
- A ready result confirms these observable prerequisites only. Managed Appium process startup, device-side UiAutomator2 session initialization, automation permissions and Case-specific UI success remain execution concerns, clearly disclosed rather than reported as checked.


### iOS diagnosis

- Ordered details are `xcode_installation`, `xcode_developer_directory`, `appium_connect_runtime`, `device_connection`, `device_selection`, `wda_signing`, `application_identifier`, `application_path`, and `application_installation` on macOS hosts (or `not_applicable` on non-macOS hosts).
- `xcode_installation` and `xcode_developer_directory` verify full Xcode installation and active full-Xcode developer directory (`Contents/Developer`). `appium_connect_runtime` performs strictly read-only, zero-subprocess, zero-network static inspection of `appium-connect-agent` package importability, unambiguous `node` executable resolution on `PATH` (without reading `~/.appium`), and `~/.appium-connect-agent/` (`records/installation.json` complete with verified Appium 3.7.0, idle/settled `records/service.json` and `records/maintenance.json`, and compatible installed `driver-home/node_modules/appium-xcuitest-driver` via `Runtime.diagnose(target_driver="xcuitest")`), supplying explicit copyable Python API repair commands (`Runtime(LocalSettings()).install(InstallRequest())`, `Runtime(LocalSettings()).ensure_managed_driver("xcuitest")`, `Runtime(LocalSettings()).cleanup_installation()`).
- `device_connection` and `device_selection` inspect bounded read-only `list_ios_devices()` inventory without booting Simulators or starting WDA/Appium. Usable targets are `simulator` in `booted` state or `device` in `connected` state; other states remain visible with actionable guidance. An explicit `udid` must match one usable target. Quick Test requires explicit selection; the existing sole-usable-device rule applies only to callers that do not require explicit selection.
- `wda_signing` requires valid, nonblank `xcode_org_id` and `xcode_signing_id` for a selected usable physical device; optional `updated_wda_bundle_id` is validated when supplied and never generated. For a Simulator it is not applicable; without a usable selected device it is blocked by selection. The prerequisite runs independently of application identification and reports missing/invalid configuration with safe local setup guidance, never returning configured values. Readiness checks only supplied configuration, not certificate, provisioning, or WDA launch success.
- `application_identifier` and `application_path` validate configured `bundle_id` and `.app`/`.ipa` path shape/consistency (with at least one required). When the selected usable target is a booted Simulator and a `bundle_id` is configured without a standalone `.app`/`.ipa` installable bundle path, `application_installation` runs a bounded read-only `simctl appinfo <udid> <bundle_id>` check to distinguish installed vs absent Simulator apps; when an explicit `.app`/`.ipa` path is supplied or a physical device is selected without host-side read-only package certainty, `application_installation` reports `not_applicable` with clear execution-boundary disclosure rather than guessing installation state.

### Windows Sandbox diagnosis

- When `sandbox=None` (default), Windows returns an empty prerequisite tuple so standard host execution does not require Windows Sandbox.
- When `sandbox="wsb"` on `platform="windows"`, Windows prerequisite diagnosis performs bounded, strictly read-only inspection without starting a Sandbox instance or mutating host state, returning ordered facts: `windows_sandbox_cli`, `windows_sandbox_service`, `windows_sandbox_slot`, and `windows_sandbox_runtime`.
- `windows_sandbox_cli` verifies a Windows (`win32`) host and resolves `wsb.exe` (`PATH` or `%SYSTEMROOT%\System32\wsb.exe`). On non-Windows hosts or when `wsb.exe` is absent, downstream `wsb.exe` service/slot probes report `not_applicable` (`windows.dependency_unavailable`) while independent local runtime checks still run on Windows hosts.
- `windows_sandbox_service` runs a bounded read-only `wsb.exe list --raw` query (without `wsb start` or `wsb connect`) and validates JSON object output containing a `WindowsSandboxEnvironments` list, distinguishing timeout, invocation failure, nonzero exit, and malformed output with safe remediation guidance.
- `windows_sandbox_slot` inspects the `WindowsSandboxEnvironments` list from the same `wsb.exe list --raw` probe (reusing the single query without spawning `wsb.exe` twice) and reports `unavailable` (`windows.sandbox_busy`) when an active Sandbox environment already occupies the host's single-instance slot.
- `windows_sandbox_runtime` performs zero-subprocess filesystem inspection of the host base Python (`<base_prefix>/python.exe`), readable `site-packages`, and required x64 C++/MFC runtime DLLs (`mfc140u.dll`, `msvcp140.dll`, `vcruntime140.dll`, `vcruntime140_1.dll`) across `%SYSTEMROOT%\System32`, base Python, and `pywin32` directories.
- When `sandbox="wsb"`, `PlatformRuntimeService.check_target_availability` for Windows incorporates any `unavailable`, `error`, or dependency-blocked (`windows.dependency_unavailable`) Sandbox prerequisite failure before reporting target availability ready.
## Current Invariants

- Current host support behavior remains unchanged.
- Windows discovery covers Chromium and Chrome/Edge stable, beta, dev, and canary through exact paths.
- Explicit Web validation delegates to the pure Models identity contract and never trusts a shared basename or generic substring.
- Candidates are normalized, deduplicated, ordered, and never selected when multiple distinct matches exist.
- The module does not provision targets, start services, authenticate, mutate Workspaces, or expose subprocess output.
- macOS checks never install Xcode, accept its license, run first-launch setup, change `xcode-select`, install npm packages or Appium drivers, grant Accessibility/Automation permissions, start Appium, launch the target application, or create an Appium session.
- Environment diagnosis does not inspect Provider readiness; Workspace Doctor composes Environment facts with other public readiness boundaries.
