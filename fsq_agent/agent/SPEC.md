# Module: agent

## Purpose

Provide SDK-neutral dynamic Goal/reference orchestration used by `execution`: load runtime settings, knowledge, and skills; derive execution key actions and a final verification goal through an injected Coding Agent runtime; persist safe normalized events; coordinate main runtime and evidence-based verification calls; and derive final verification status. FSQ request/tool/event assembly belongs to `adapters.coding_agent`; concrete inference-client construction, model invocation, tool loops, and raw protocol conversion belong to `agent_engine`. Complete operation coordination, transport cancellation, report publication, and candidate Case recording belong to `execution`.

## Dependencies

- `models`: Uses all task, plan, structured agent IO, result, tool, report, event, and exception models.
- `config`: Uses runtime settings.
- `providers`: Prepares shared OpenAI, Azure OpenAI, DeepSeek, Google Gemini, or GitHub Copilot access and refreshes provider-local runtime credentials at dynamic task startup.
- `core`: Uses `CapabilityRegistry`, `StepRunner`, `HarnessInterface` implementations, platform CommonTool providers, backend drivers, and shared harness behavior through public core exports supplied by entry/runtime construction.
- `tools`: Builds dynamic-only AgentTool providers/executors and neutral tool bindings.
- `observation`: Captures evidence after steps.
- `knowledge`: Loads private knowledge.
- `skills`: Loads configured automation skill instruction bundles.

The agent module consumes SDK-neutral models and public runtime protocols. It does not import adapters, OpenAI/Agents/Google GenAI SDK types, concrete SDK runtime classes, `capabilities`, or decorator internals. All construction paths require an injected `CodingAgentRuntimeFactory`.

## Public Interface

Current `__init__.py` exports via `__all__`:

- `FsqAgent`: Main orchestration class.
- `CodingAgentRuntime`: Protocol for pre-plan, main execution, and evidence-based verification using SDK-neutral inputs and results.
- `CodingAgentRuntimeFactory`: Composition contract for creating a runtime from validated settings and optional harness construction input.
- `CodingAgentPolicy`: Public SDK-neutral facade for pre-plan instructions and knowledge lookup schemas, prompt construction, structured-output coercion/serialization, and verification evidence construction used by Coding Agent adapters.
- `Verifier`: Parses structured verifier-agent or runner final output and converts task status, evidence, and diagnostics into a `VerificationResult` for the task's single `verification_goal`.
- `check_dynamic_agent_readiness(settings: Settings) -> tuple[bool, str, str]`: Doctor-facing static readiness operation. It validates dynamic Agent settings, prompt templates, configured knowledge roots, required Skills, AgentTool policy, and active platform capability construction without refreshing Provider credentials, sending model inference, creating a Harness/Driver/session, starting an application, or writing run artifacts. Optional unusable Skills follow the existing loader contract; required unusable Skills make readiness unavailable. It returns only a safe normalized verdict, message, and action and does not expose loaded knowledge, Skill content, prompt content, paths, credentials, or exception details.

Current public call shape:

- `FsqAgent.from_settings(settings: Settings, runtime_factory: CodingAgentRuntimeFactory, ...) -> FsqAgent`
- `FsqAgent.run_in_context(task: Task, context: RunExecutionContext, event_sink: RunEventSink | None = None, *, evidence_sink, cancellation_check=None) -> DynamicAgentOutcome`: executes within an allocated Run and returns separate execution/verification facts. Managed entry points use Execution; no allocating or report-producing `FsqAgent.run` shortcut is exposed.
- Runtime context binding accepts the supplied `RunExecutionContext`, shared evidence sink, and cancellation boundary before external actions; runtime lifecycle/result ownership remains outside Agent.
- `CodingAgentRuntime.run_task(task: Task, knowledge: KnowledgeBundle, skills: list[SkillBundle], run_id: str, event_sink: RunEventSink | None = None) -> list[StepResult]`
- `CodingAgentRuntime.run_verification(task: Task, results: list[StepResult], run_id: str, events_path: Path | None, event_sink: RunEventSink | None = None) -> list[StepResult]`
- `Verifier.verify(task: Task, results: list[StepResult], events_path: Path | None = None) -> VerificationResult`

## Internal Structure

- `__init__.py`: Public exports only.
- `_core.py`: `FsqAgent` orchestration and lifecycle.
- `_events.py`: Run event emission, sequencing, persistence fan-out, and user-sink dispatch.
- `_runtime.py`: SDK-neutral Coding Agent runtime and factory protocols.
- `_policy.py`: Implementation of the public `CodingAgentPolicy` facade over Agent-owned planning, prompt, structured-output, and verification-evidence policy.
- `_pre_plan.py`: Internal prompt instructions and helpers for dynamic goal planning from loaded skills, optional project knowledge, optional page index knowledge, and on-demand page knowledge when invoked by `FsqAgent.run_in_context`.
- `_prompt.py`: Prompt model construction and template rendering for agent instructions and task input.
- `_structured_output.py`: Shared coercion helpers for structured agent final output values and compatibility parsing of legacy/raw final JSON strings.
- `_verification_task.py`: Builds an evidence bundle from task context, execution records, event logs, and persisted tool artifacts for a separate evidence-based verification agent task.
- `_verifier.py`: Evidence-based goal verification and failure diagnostics.
- `_readiness.py`: Doctor-facing static dynamic-Agent readiness composition with no external session creation or model invocation.
- `SPEC.md`: Module design.

## Platform Runtime Blocks

Shared runtime rules:

- `DefaultCodingAgentRuntime` builds the active harness through `core.HarnessFactory`, which composes the platform CommonTool provider and config-selected backend driver from `settings.harness.platform` and backend settings.
- Neutral tool bindings are generated from dynamic-only AgentTools plus the active platform CommonTool/PlatformTool `action_space()`; `agent_engine` owns their inference-protocol conversion.
- Runtime construction builds or receives the active runtime secret store from the current workspace settings snapshot. Pre-plan and main execution model input include safe runtime-secret names, never values. The runtime must not read workspace secrets from global environment or expose `get_runtime_secret` as a normal LLM action tool.
- The runtime remains decoupled from platform decorator internals and backend SDK APIs.

Android runtime:

- Uses `HarnessFactory` to compose the private Android harness, `CommonPlatformTools`, and the config-selected Android driver.
- Startup metadata includes safe Android app id and serial presence.
- Expected platform skill is `android-harness.md` when configured.

Web runtime:

- Uses `HarnessFactory` to compose the private Web harness, `CommonPlatformTools`, and the config-selected Web driver.
- Startup metadata includes safe Web backend, channel, browser executable configured state, headless, and base URL presence.
- Harness construction must not launch a browser. Dynamic Web runs receive `start_browser` and `close_browser` as normal harness tools, and the runtime must not auto-call or auto-inject them.
- Expected platform skill is `web-harness.md` when configured.

macOS runtime:

- Uses `HarnessFactory` to compose the private macOS harness, `CommonPlatformTools`, and the config-selected macOS driver.
- Startup metadata includes only safe macOS fields: platform, backend, bundle id presence, app path presence, action timeout seconds, driver class, and configured skill names. It must not log local paths when they are considered sensitive by configuration policy or any secret environment values.
- Harness construction must not connect to Appium or launch a macOS application. Dynamic macOS runs receive `launch_app` and `kill_app` as normal harness tools, and the runtime must not auto-call or auto-inject them.
- Expected platform skill is `macos-harness.md` when configured.
- macOS execution guidance uses structured `ui_snapshot` queries for semantic element discovery and treats raw artifact text search as historical recovery only. Exhausted or truncated matches do not justify skipping a requested action; a bounded refinement or fresh observation precedes a limitation report.
- Explicit macOS element-only requests prohibit fallback to `assert_with_ai` or screenshot-inferred coordinate actions. Resolving an element and acting on its current geometry remains element-based. Missing element evidence is reported rather than replaced with a visual guess. This policy is expressed in the configured macOS guidance, not a keyword-based tool-filtering branch in the shared runtime.
- User-required result filters and their order remain execution obligations. Product-detail variant selection cannot substitute for filtering the result list, and dependent comparison or purchase actions do not proceed while required filter state is unverified. Recovery retries the same semantic action; a non-equivalent fallback leaves that action unmet. Existing cart contents do not prove that the current Run added a product.
- macOS guidance preserves explicit user method constraints in planning and evidence-based outcome claims without inventing additional final-verifier requirements from generated key actions. When permitted element-based recovery cannot complete a required step, the main agent stops dependent actions and reports the blocking step; final status retains the existing goal/evidence rules.

## Python Architecture

- Architecture level: 3 Layered Application.
- Public API: `FsqAgent`, `CodingAgentRuntime`, `CodingAgentRuntimeFactory`, `CodingAgentPolicy`, and `Verifier` exported from `__init__.py`. Concrete Coding Agent runtimes are selected only by adapter composition roots.
- Internal modules: all `_*.py` files are private implementation modules.
- Domain boundaries: this module owns SDK-neutral in-context dynamic orchestration, pre-planning policy, safe progress persistence, and verification policy. FSQ runtime assembly and neutral-event projection belong to `adapters.coding_agent`; raw inference protocols belong to `agent_engine`; Run allocation, frozen outcomes, reports, and recording are coordinated by `execution`.
- Boundary models: all tasks, final outputs, events, capability metadata, runner results, and report artifacts come from `models`.
- Dependency direction: may depend on `models`, `config`, public Core contracts, `providers`, `tools`, `observation`, `knowledge`, and `skills`; it must not import `execution`, `report`, `application`, adapters, or SDK packages. Execution invokes Agent through its public API and composition roots inject the adapter runtime factory.
- Rationale: dynamic orchestration coordinates providers, harnesses, tools, persisted progress, and verification without owning Run lifecycle, warranting Level 3 without repository/unit-of-work patterns.

## Error Handling

Configuration errors are raised before task execution when required runtime configuration or provider credentials are absent, required skills fail to load, harness/platform tool construction fails, AgentTool construction fails, or platform action-space conversion fails. Engine, harness, AgentTool, CommonTool, or PlatformTool runtime exceptions are converted into failed `StepResult` values so report generation can still complete. Synchronous harness construction during main execution startup is bounded by `agent.step_timeout_seconds`; timeout or construction failure emits a run failure event and returns a failed runner `StepResult` instead of waiting silently. Recoverable tool failures should be surfaced through structured final JSON. Verification treats invalid final JSON as inconclusive instead of claiming task success.

Main-execution turn-budget exhaustion uses the Coding Agent adapter's runtime-generated inconclusive `task_run_v1` terminal envelope rather than a failed generic runner record. Agent derives an inconclusive `VerificationResult` with the same nonempty termination summary and runtime-authorship diagnostics, without a further verifier inference or any claim that the goal was achieved. The successful summary-record status describes envelope completion only. This bounded termination is not inserted into `DynamicAgentOutcome.errors` as a fatal runtime error; independent infrastructure, evidence, cancellation, and pending-cleanup failures retain their existing precedence. Ordinary model-produced conclusions retain the existing evidence-based verification path.

Internal goal planning raises configuration errors when agent-runtime configuration is unavailable and planning errors when the runtime does not return a valid `GoalPrePlan`. Malformed JSON, invalid output contracts, and unavailable inference remain technical failures; a valid open-ended request is not a planning failure merely because it lacks a rigid assertion. Structurally valid plans with blank verification text use a built-in evidence-grounded delivery criterion preserving the original request's explicit constraints. Planning used inside `FsqAgent.run_in_context` does not construct platform harnesses, call UI/external action tools, or generate reports. Missing optional project knowledge, page index knowledge, or page files are not model-facing instructions. Read-only knowledge failures are structured tool results so planning can continue when possible.

During `FsqAgent.run_in_context`, provider-local credentials are prepared once before pre-plan without replacing resolved platform policy. GitHub Copilot preparation delegates the shared cache-first, 60-second safety-window and bounded remote-refresh policy to Providers; a reusable cached bearer token does not trigger network refresh or configuration writes. Runtime surfaces use only cached explicit OAuth credentials and never start device authentication. Prepared credentials are reused by pre-plan, main execution, verification, and visual assertions while preserving the task's Provider/effort snapshot. Planning uses explicit reference text/kind with the existing goal/description compatibility fallback, converts returned `GoalKeyAction` values into `Task.key_actions`, and copies the effective single `verification_goal` onto the task. Request-grounded flow guidance and a delivery criterion fill blank fields for legitimate open-ended work without inventing actions or acceptance conditions; unusable original intent or technical planning failure still fails before external UI actions. Generated actions are guidance, not extra verifier requirements.

The terminal `run_failed` event emitted by `FsqAgent.run_in_context` preserves `exception_type` and adds optional flat payload fields `error_code`, `reason`, `status_code`, and `errno` only for `FsqAgentError`. `error_code` is selected from a fixed mapping of known domain exception classes, not arbitrary exception text or attributes. `reason` accepts only `invalid_candidate`, `authentication`, `access_denied`, `rate_limited`, `timeout`, `network`, `malformed_response`, `storage`, or `internal`; unknown values are omitted. `status_code` accepts only an actual integer in 100..599, and `errno` only an actual positive integer from structured context or an `OSError` in a cycle-safe cause chain of at most eight exceptions; booleans are not integers for this projection. Missing or invalid fields are omitted, not inferred from messages. Other exceptions retain the existing class-only diagnostic.

Failure event projection never copies the complete exception context, raw exception/cause text, traceback, response body, headers, cookies, tokens, credential values, paths, or task/model content. These additive fields use the existing `RunEvent.payload` and event redaction/persistence pipeline without a new event type or model schema. Diagnostic projection or sink failure does not replace or suppress the original failure or cancellation, which is re-raised unchanged. Credential-preparation attempts and waits do not extend the owning operation's deadline or change task, action, inference, or turn budgets.

## Current Invariants

- The orchestration module depends on all leaf modules, but leaf modules never depend on `agent`.
- `agent_engine` supplies neutral model and agent-execution protocols; its private backends own OpenAI Responses and Google Interactions requests and use shared local tool continuation.
- OpenAI, Azure OpenAI, DeepSeek, Google Gemini, and GitHub Copilot configured access is delegated to `providers`. `agent` asks for cache-first provider-local credential preparation once at dynamic task startup; the injected runtime consumes selected neutral models. Authentication, refresh/retry timing, model discovery, endpoint selection, token caching, plan detection, and concrete inference-client construction are not implemented in `agent`. OpenAI, DeepSeek, and Gemini task preparation use saved configuration without a model-list request, and active tasks retain their prepared Provider snapshot.
- Task execution requires an available engine backend and provider authentication through `providers`, without an OpenAI Agents SDK runtime dependency. There is no offline fallback execution path.
- The private engine owns the sole function-tool dispatcher and turn-continuation loop; Agent and its adapters do not duplicate that loop.
- Neutral tool bindings are generated from validated AgentTool definitions plus active platform CommonTool/PlatformTool `action_space()` schemas. The FSQ runtime preserves canonical names, parameter schemas, descriptions, and default strictness; private engine backends convert bindings into native protocol definitions and the shared loop dispatches their callbacks. Per-capability schema strictness is not capability metadata, and unimplemented backend methods must not appear in `action_space()`. Runtime requests contain no external platform tool servers. `assert_with_ai` is a driver-backed PlatformTool with an injected `ai_services` evaluator, not an AgentTool or concrete harness method.
- The runtime forwards resolved `agent_runtime.reasoning_effort` to all business requests; Agent Engine owns explicit native mapping for both backend families and continuation. Responses Agent verbosity remains independently medium; no generation defaults or SDK-specific settings bypass the neutral effort contract.
- `DefaultCodingAgentRuntime` constructs the active harness through `HarnessFactory` from `settings.harness.platform`. Driver selection is delegated to `DriverFactory`, which chooses the private concrete backend from config-owned platform backend settings. The runtime must not inspect Playwright APIs, Appium APIs, MCP reference code, or decorator internals when exposing tools; it uses `harness.action_space()` and `StepRunner` like every other platform.
- Web browser lifecycle is task-visible capability behavior. The runtime may construct a Web driver object for tool exposure, but it must not launch a browser until the agent executes `start_browser`, and it must not treat final resource cleanup as evidence that `close_browser` was executed.
- The runtime treats decorators as compile/bootstrap-time declaration mechanics only. It consumes `CapabilityDefinition` values, `CapabilityRegistry` snapshots, and `StepRunner` results, and it must not inspect decorator marker attributes or platform action catalog entries directly.
- Main execution startup is observable before the first model planning turn. `DefaultCodingAgentRuntime.run_task` emits runtime progress events for startup, harness setup, tool setup, and agent-runtime readiness before the main `Planning started` event. Harness setup events include only safe metadata such as platform, backend, app id presence, serial presence, Web channel, Web browser executable configured state, headless mode, base URL presence, macOS bundle id/app path presence, timeout seconds, configured skill names, and driver class when available.
- Harness construction remains a synchronous platform concern internally, but dynamic main execution wraps it in an async-compatible timeout boundary. The runtime calls the configured harness factory or built-in harness construction through a worker-thread helper and applies `agent.step_timeout_seconds` as the startup timeout. A timed-out worker result is ignored after the runtime has returned a failed runner step; no UI action should be invoked from that timed-out path.
- The capability tool adapter must preserve capability provenance, including canonical capability name, executor kind, step kind, platform, backend, owner, replay policy, sensitivity, and authored-action metadata when present, in run events and tool result metadata. Primary authored strict command names come from `ReplayPolicy(kind="fsq_command").alias` rather than a duplicate capability alias list.
- When the engine invokes a CommonTool or PlatformTool binding, the platform adapter receives neutral JSON-object arguments, builds an `ExecutableStep` with the canonical capability name, and delegates to `StepRunner.run_step(run_id, step)` rather than invoking providers, harnesses, or drivers directly. StepRunner owns screenshot/UI-snapshot policy and post-action delay, derived from capability metadata, `ExecutableStep.kind`, and configured timing. Dynamic execution and strict replay share this policy without private action-name allowlists or `CapabilityDefinition.capture_evidence`. `action` captures before and after, `assertion` before only, `setup` after only, and `teardown` before only, including CommonTool actions such as `wait_ms`. Automatic capture writes `screenshot` plus normalized `ui_snapshot`; observation and diagnostic capabilities receive no automatic screenshot capture.
- The shared capture policy has an explicit Run-scoped action-before switch, default true. Execution disables it for dynamic `record=False`; Agent forwards the context unchanged. Only automatic action prepare capture is omitted; validation, cancellation, hooks, finalize eligibility, assertion capture, recording-enabled dynamic execution, and Strict behavior are preserved.
- A capability failure should normally be returned as a successful engine tool callback result whose JSON has `status="failed"`, `failure_category`, `error_message`, output preview, artifact refs, and safe capability metadata. Runner-level artifact capture failures must surface as failed capability tool JSON with `failure_category="artifact_error"`. Unexpected adapter failures are converted into structured failed tool JSON or failed `StepResult` records depending on when they occur. Tool output events should include safe structured payload fields for `capability_name`, `executor_kind`, `step_kind`, `platform`, `backend`, `owner`, `replay`, `sensitivity`, effective post-action delay metadata, status, failure category, safe replay params, dependency metadata, and artifact paths when known so CLI recording does not parse truncated previews.
- Internal capability callback JSON and structured RunEvents preserve report/recording fields including `tool_name`, `tool_origin`, `platform`, `driver_method`, `fsq_action_name`, `status`, `failure_category`, `error_message`, `duration_ms`, `result`, and `metadata`, and authoritative `capability_name`, `executor_kind`, `step_kind`, `replay`, `sensitivity`, effective delay metadata, `safe_replay_params`, `runner_step_id`, `runner_result`, and flattened `artifact_refs`. The adapter may supply a compact model-request-only projection without changing internal records or durable facts.
- Capability registry bootstrap or engine tool conversion failures are startup configuration errors. The runtime must not silently expose a partial capability list.
- The agent may create an internal plan before external actions, use the pre-plan-derived `verification_goal` as the final success target, execute through AgentTools plus active CommonTool/PlatformTool capabilities, and adapt the plan when tool feedback changes the best path.
- Standalone goal pre-planning is not a public CLI or module API. Any retained pre-planning implementation is internal to normal LLM execution.
- Internal planning receives a structured reference envelope containing `reference_type`, `reference_text`, successfully loaded configured skills, optional non-blank `project.md` knowledge from the workspace knowledge root, optional `index.md` page knowledge from the resolved workspace pre-plan knowledge directory, and a concise active CommonTool/PlatformTool capability summary generated from the active platform registry. It returns ordered key actions, one verification goal, relevant page ids, summary, and warnings. It is side-effect-free for the application under test: no UI automation, no lifecycle calls, no verification agent, and no separate report generation.
- For `reference_type="raw_case"`, the pre-planner treats the complete raw case text as advisory source material, not as parsed strict executable input. It should prefer case-level intent signals such as name, metadata, tags, properties, and human-authored goal text when summarizing `verification_goal`; raw YAML steps may support execution planning and fill gaps, but they are not assumed accurate or complete and must not be transformed into final verifier requirements. If step details conflict with case-level intent, the case-level intent wins and the mismatch should appear in warnings. Lifecycle commands such as `launchApp`, `killApp`, `startBrowser`, and `closeBrowser` may be represented as setup/teardown intent instead of ordinary business key actions unless they are semantically central to the case.
- Pre-planning preserves an unsubmitted, unsaved, or unsent terminal state only when the goal explicitly requests that restriction or a draft state. Otherwise, when creating an entry, applying settings, or answering an interactive form/challenge requires a clear submit/save/confirm control to make the requested result effective, the completion path includes that control and verification of the resulting state. Absence of the literal words "click Submit" is not an implicit draft instruction; planning never invents "without submitting". Explicit no-save/no-submit/no-send instructions take precedence, without authorizing unrelated or destructive confirmations.
- For click-to-reveal observation sequences, the initially visible item, subsequent valid displayed items, and the transition to an answer/submission form are normal observed state-machine progression. Planning directs execution to use the complete actually observed valid sequence, not invent a further item or treat the final form transition alone as unresolved ambiguity; genuinely missing or contradictory observations remain unverified. Computation and any required authorized submission are followed by result-state verification.
- Generated key actions preserve each usable action's existing text/order and append its complete trimmed nonempty notes to the same entry without extra inference or arbitrary clipping. Blank notes do not change rendering. Explicit caller-provided actions remain unchanged even when pre-planning supplies a missing verification goal. Prompt and verifier-evidence construction preserve this guidance; final verification checks only the pre-plan-derived `verification_goal` against execution evidence.
- Pre-planning is an iterative knowledge loop. The initial model input contains configured skills that load successfully, `project.md` when present, and `index.md` when present. The pre-plan agent can call read-only local knowledge tools to reload available project/index entries or load specific page files from the resolved pre-plan knowledge directory by page id or relative path. Page-to-page transitions may cause additional page reads until the action chain is complete or no useful next page is available.
- If optional project or page knowledge is incomplete or absent, the planner should still produce the best available contiguous key-action chain and a fact-supported verification goal from the reference text, loaded skills, active platform tool summary, and any available knowledge. It may skip at most one consecutive missing action by recording a warning. Authorized browsing, information viewing, and exploration use an observable flow-delivery goal without inventing an objective state change. Valid blank planning fields for such requests receive request-grounded flow guidance and the built-in evidence-based delivery criterion; malformed output and intent with no usable authorized scope remain failures rather than fabricated plans.
- When a caller supplies ordered key actions, the runtime must use the complete list as the execution spine: preserve their relative order, allow recovery/setup/dialog-handling steps between them, and collect live evidence for the resulting state before reporting success. The public CLI no longer supplies parsed FSQ command-derived key actions for normal LLM `--case-yaml` or `--case-dir` runs.
- Ordered key actions must preserve semantic fidelity. Recovery or fallback actions may restore UI state, but they do not satisfy the original ordered key action unless they perform the same accepted semantic action. Tool usage errors should be corrected for the same semantic action before switching to non-equivalent fallback routes.
- Default execution guidance uses supplied write budgets economically, reserving only goal-required commits and never prohibited saves/submissions. Candidate facts and coverage survive page transitions in concise plan/context records; goal-defined visible differences permit early exclusion, while aggregation/subset tasks retain potentially contributing values. Paging/deletion invalidates old viewport positions. Search progression is bounded by observed exhaustion/blockage and supplied limits; clipped presentation alone does not justify replaying a verified input.
- Execution uses a pre-act ledger for multi-item transcription, filtering, counting, and subset selection: obtain complete relevant source values with minimal read-only observations, distinguish actual content from presentation metadata, preserve exact text and units, compute the requested subset or aggregate, and only then perform writes. Clipped snapshots require a complete permitted read before exact transcription; presentation labels are not blindly stripped from real content. Coverage, totals, and candidate identities survive navigation, and failed or unknown-acceptance writes are not replayed without fresh state inspection.
- Before submitting the final result, the main agent reads back goal-relevant persisted content, complete file identity, destination, duration bounds, and absence of accidental extras, correcting observed mismatches while the Harness is still open and authorized actions remain possible. Explicit drafts and no-save/no-send constraints take precedence. Only a valid tool-root `write_budget` receipt activates write-throttling guidance and completion reserves; absent or invalid receipts impose no write limit or budget-based stop. Reserves belong to the main agent, never a post-close verifier repair phase.
- After one target-identity ambiguity or input-focus click failure, execution does not repeat the unchanged ambiguous locator. It refreshes observation and uses a uniquely identifying attribute combination or a fresh, attributable physical bounds-based focus action; unknown-acceptance text entry requires readback before another write. For notes/documents, absence of rename in the editor menu leads to a file-list long press on the identified file. Dynamic-video extraction uses observed playback controls and paused temporal sampling rather than repeatedly restarting playback or claiming unseen frames.
- Dynamic execution receives a required, already allocated `RunExecutionContext` and evidence sink from Execution, uses the same identity for planning, runtime calls, verification, and progress, and returns `DynamicAgentOutcome`. Agent never allocates metadata, freezes outcomes, generates reports, or advances lifecycle. Artifacts remain under the supplied platform Run root. AgentTools and synthetic planning/runtime summaries are not evidence capability executions.
- Actual capability results reach Core Evidence through the bound sink independently of model progress. Agent `events.jsonl` remains a redacted progress channel, never a replacement execution journal. A progress-sink failure after execution facts are durable does not erase those facts; required evidence failures remain distinguishable from action or verification failures.
- Task runs emit live `RunEvent` values for planning summaries, AgentTool calls, CommonTool/PlatformTool capability calls, runtime-internal progress, tool outputs, failures, and completion. Events are for user-visible progress, reports, and post-run recording metadata, and must not expose hidden model chain-of-thought. Runtime interruptions such as debugger cancellation or keyboard interrupt emit a final `run_failed` event before being re-raised.
- The runtime consumes neutral `AgentEngine` semantic events and maps them into `RunEvent` values while preserving final output used by verification and reporting. Responses/Interactions streaming and raw event conversion remain private to the engine.
- The runtime passes an effective tracing choice that requires both `agent_runtime.tracing_enabled` and a nonblank `OPENAI_API_KEY`. The engine applies that choice without exposing private tracing objects; absent export credentials do not produce repeated trace-export warnings.
- Runtime requests configure one FSQ filter over ordered raw tool-output entries. Inline count and character budgets apply to compact model-facing projections; complete original historical outputs are persisted under the Run tool-artifact directory. Non-inline content uses concise artifact references. Event/recording/Verifier/report data remains complete and independent of projection. No user-turn trimming or vendor transcript dictionaries are exposed to this policy.
- The filter preserves existing artifact content, sensitive-output handling, call IDs, and ordering. The engine applies known-entry output replacements only, leaving unrelated messages and internal model state unchanged.
- A Dynamic Agent main execution terminal outcome emits one `dynamic_agent_token_usage` Run event from the Coding Agent adapter when `AgentResult` supplies usage. The event is persisted through the same Agent event pipeline as other Run events, represents only main-execution usage, and contains no prompt, response, credential, or inferred token data. Pre-plan and final verification do not emit this event.
- Visual assertion image handling belongs to the backend `assert_with_ai` PlatformTool and injected evaluator using harness evidence services, not a local `submit_visual_assertion` or next-turn screenshot filter. Android, iOS, and macOS share the assertion's sole privacy-approved capture with step evidence, keep their host capture provenance, and retain inconclusive outcomes as incomplete/unverified. Web and Windows visual capture and verdict behavior is unchanged.
- Runtime instructions tell the agent that AgentTool outputs may include artifact references and that `search_artifact`/`read_artifact_slice` should be used for targeted recovery rather than full artifact rereads. Artifact search is historical context and should not be treated as proof of current UI state without a fresh tool observation.
- Runtime instructions tell the agent to treat inferred FSQ preconditions as conditional setup obligations. It must inspect live UI/account state first, execute missing setup before ordered key actions, use `textType: runtimeSecret` with one of the listed workspace secret names for credential text entry, avoid shell-style placeholders such as `${TEST_ACCOUNT_EMAIL}`, and never echo secret values in progress events, evidence, or final output.
- Runtime instructions and task input are assembled by first building prompt models, then rendering Jinja template files configured by `agent_runtime.prompt.agent_template_path` and `agent_runtime.prompt.task_template_path` or the package defaults. Static behavioral prompt text and section wording belong in template files, while configuration injects only scalar variables and optional template paths. There is no custom-instruction prompt channel; project-specific guidance is loaded from knowledge, and reusable execution guidance is loaded from configured skills.
- Model-facing runtime instructions must not include knowledge-loader warnings or skill-loader warnings. Required skill load failures fail before LLM execution. Optional broken skills are skipped with operator-visible diagnostics and are not included in main execution instructions or pre-plan skill input.
- The default `agent_instructions.j2` should stay a compact dynamic execution contract: non-interactive single-task execution, configured tool boundaries, ordered key action semantics, goal-only final verification, source-case mutation boundaries, secret handling, artifact/evidence boundaries, structured-output semantics, and separate blocks for project knowledge and successfully loaded skills.
- Runtime Markdown content under the selected workspace platform's `knowledge/<platform>/` root is part of prompt quality. Its `project.md` is optional and omitted when missing, empty, or whitespace-only. Reusable preset-configured skills remain independent repository resources; only complete loaded skills are included in model-facing pre-plan input.
- Dynamic orchestration uses the current workspace settings snapshot for platform target, cases, knowledge, direct-child run directory, and private secret values. Redaction consumes the same private values as `RuntimeSecretStore`; it must not rediscover workspace secrets through `os.environ`.
- If the user description is too broad to derive domain-specific checks, the default success standard is that the executable task flow completes without unrecovered errors and with enough evidence to show completion.
- Skills are descriptive guidance. Command execution is not exposed through configured CLI tools or SDK `ShellTool`; execution is performed through AgentTools and active CommonTool/PlatformTool capabilities only.
- Harness- and platform-specific action selection, argument rules, and recovery recipes belong in configured skill Markdown rather than hard-coded agent runtime branches. Android runs should load `android-harness.md`; Web runs should load `web-harness.md`; macOS runs should load `macos-harness.md`; iOS runs should load `ios-harness.md` alongside common automation guidance. The agent consumes those skills as current runtime policy while remaining decoupled from concrete platform backends.
- The final engine output must conform to `AgentFinalOutput`. The FSQ runtime derives a neutral output contract from that authoritative Pydantic model and its parser; the private engine supplies its strict schema to Responses and validates final text through the supplied parser. Prompts describe business semantics without duplicating full JSON Schema text.
- Final output includes `schema_version` for traceability. Schema selection is not configurable; the runtime owns the current contract.
- For an answer-producing task, `AgentFinalOutput.summary` contains the best evidence-supported answer in the requested format, including required unit conversion and rounding. Missing coverage or residual uncertainty is recorded separately in claims, errors, or evidence notes; it neither erases an available answer nor turns a provisional answer into verified success. Near the turn boundary or a valid supplied write budget with `remaining <= 1`, delivery preserves that available answer instead of replacing it with a disclaimer. Without supporting evidence the agent must not invent an answer. Agent-owned prompt and closing policy apply in both ordinary and externally budgeted runs and are supplied to adapters only through `CodingAgentPolicy`.
- The runtime converts `pre_plan` entries from typed final output into `StepResult` records, then appends one `agent_runtime.runner` summary step containing the serialized final output. Verification-input construction and local verification consume these current-run markers; verification summaries use `agent_runtime.verifier`. These names do not rename historical records or represent real capability calls.
- Task input is rendered from an `AgentTaskInput` model so the model-facing task envelope has a stable shape while still allowing template customization.
- Neutral engine events are mapped into `RunEvent` values preserving real capability/tool names, call IDs, redacted arguments, output previews, errors, timing, executor/origin facts (`agent_tool`, `common`, `platform`, `runtime`, or `unknown`), and safe replay/provenance metadata. They are the single model-tool event source during streaming; adapter-local duplicates are disabled. Reports reconstruct real calls from those events rather than plan/summary records. CLI recording may consume persisted capability events, but Agent does not decide eligibility or write Cases. AgentTool events remain report/diagnostic facts ignored by the recorder.
- Task execution is non-interactive. Any human-in-the-loop SDK feature must be disabled or backed by deterministic programmatic approval.
- Final result judgment is performed by a separate evidence-based verification agent task after the main automation run. The verification task has no AgentTools, no CommonTool/PlatformTool action tools, and no image inputs; it receives the authoritative pre-plan-derived `verification_goal`, the main agent's structured claims when available, execution records, normalized event/tool-call records, AI assertion verdict metadata, and persisted artifact excerpts. The verification agent must decide success, failure, or inconclusive from supplied execution evidence only.
- Final verification is goal-only. Success requires evidence supporting `Task.verification_goal`; failure requires evidence proving the goal unmet or impossible; inconclusive is used when evidence is insufficient or ambiguous. Key actions are execution guidance and diagnostics, not independent final verifier requirements.
- Open-ended inspection/exploration succeeds when supplied evidence demonstrates the requested authorized flow and truthful delivery of observations without unauthorized effects. It does not require an invented QA assertion, exhaustive exploration, or an unrequested state change. Explicit exact text, objective outcomes, duration intervals, collection completeness, and absence-of-extra-item requirements remain strict, with inconclusive used when the required evidence is genuinely missing.
- An explicitly requested complete filename, including an explicit absence of extension, remains a literal identity constraint in planning and evidence-based verification. Default format suffixes and hidden-extension titles do not make a different filename equivalent. Complete saved identity and destination require actual file-list/file-management evidence. This does not authorize saving a requested draft or turn generated action notes into additional final goals.
- Visual assertions in the LLM execution loop are judged during the main execution loop when the agent explicitly calls a backend PlatformTool assertion such as `assert_with_ai` and receives the provider-backed verdict as tool output evidence. The verification task does not re-inspect screenshot pixels; it verifies that execution evidence contains the AI assertion result, that the main agent's structured output reports the corresponding result, and that no supplied evidence contradicts that result.
- Deterministic strict-core execution is not an agent capability. Strict entry-layer code may inject a provider-backed evaluator for explicitly authored `assertWithAI`, but `agent` does not own strict execution or construct strict harnesses.
- Candidate Case recording is not an agent capability. Agent persists safe event metadata needed by Application, but must not write candidate `*.fsq.yaml`, mutate source Cases, resolve replay refs, or decide whether a candidate should be produced.
- Evidence-based runtime verification is a required `CodingAgentRuntime` capability exposed as `run_verification`; Agent orchestration invokes it directly and never probes private or optional runtime methods.
- Coding Agent adapters consume Agent-owned planning, prompt, structured-output, and verification-evidence policy only through the public `CodingAgentPolicy` facade and must not import Agent `_private` modules.
- The local `Verifier` does not hard-code FSQ key-action formats or Appium command semantics as the final arbiter. A parseable verification-agent status supplies the semantic conclusion, subject to execution-owned evidence requirements: an Android, iOS, or macOS incomplete visual assertion cannot be promoted to success by runner or verifier model text or optional metadata. Without another blocking failure, its effective verification is inconclusive with the original safe assertion reason. If verification is unavailable, parseable runner output supplies the fallback; without any parseable conclusion, failed-step or inconclusive diagnostics remain the fallback.
